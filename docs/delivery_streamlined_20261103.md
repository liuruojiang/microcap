# 三版测试与发布的精简流程

本次优化只改变交付方式，不改变策略、历史数据、ST 口径或发送权限。

## 判断原则

一次交付需要证明四件事：代码身份准确、数据与交易日期正确、三版最终结果完整、实际发布结果可确认。对同一输入重复搬运或重复执行同一证明，不增加准确性。接收后的完整性验证、不同版本结果检查及独立交易日期检查不能相互替代。

## 实际执行顺序

1. 读取差异和已有回执，固定提交、数据包哈希及目标交易日；确认没有第二个写入流程。
2. 开发阶段只运行受影响行为测试。最终候选保留现有云端完整回归，不在本地另跑一遍相同全组；输入或代码没有变化、没有新失败时不加新一轮检查。
3. 三版共用一个准确提交的工作区和一份基础数据，顺序生成各自独立文件。共享基础只刷新一次，三版身份、持仓、动作和正常模式改写审计分别检查。
4. 收盘流程不再生成供兄弟版本恢复的中间基础包；三版通过后直接从共享根目录生成一个完整交付包。独立根目录的旧调用方式继续兼容。
5. 打包持有写入锁；临时 ZIP 完成语义验证、完整性及前后内容核对后才原子替换目标。归档内容必须与打包前通过验证的哈希一致，不能只检查最后恢复成原值的源文件。
6. 提交时只加入本次文件。先推送策略提交，再更新自动化的精确提交和兼容种子配置；读取远端提交并记录对应云端结果。已有相同哈希的已批准种子直接复用，不仅因发布工具变化就重打历史包、重上传或重建行情。
7. 正式主工作区同步仍使用 `refresh-all` 与独立 `check`。只有后者临时失败且前者回执、输入、输出和目标日期均未变化时，单独重试 `check`。固定日期兼容性测试不能冒充最新交易日同步。
8. 发布成功、邮件发送成功和收件成功分别记录。未请求实际发送时不追加验收邮件；超时先查询现有运行、产物或去重记录，再决定是否重试。

## 已实现的删减

| 环节 | 旧方式 | 新方式 |
| --- | --- | --- |
| 收盘代码工作区 | 三份 | 一份，三版输出保留独立文件名 |
| 兄弟版本状态恢复 | 两次整包恢复 | 零次 |
| 收盘中间基础包 | 打包、复制、上传、缓存后再恢复 | 移除；最终完整包仍保留 |
| 共享根目录最终打包 | 先复制历史目录再打包 | 直接流式打包，无历史工作区复制 |
| 最终打包基础语义验证 | 复制前后重复 | 一次；归档完整性与三版前后检查仍保留 |
| 整轮刷新重试 | 可能反复直到任务总超时 | 仅明确临时网络故障允许一次重试；永久或未知错误直接停止 |

实时流程继续保留其基础状态包和上一完成交易日锚点要求。数据源内部有界重试不变。

## 证据与边界

回归和真实固定日期打包对照记录集中在 `research_reports/20261103_delivery_streamline/`。真实对照使用已批准的 2026-11-02 包，核对全部文件集合与内容，允许变化的只有生成时刻及发布提交所在的交付记录。测试不改正式历史、不抓取全市场数据、不发送邮件。

2026-11-02 收盘后的新增公告导致普通刷新历史一致性门槛阻断，是已记录的数据问题；本次不会通过关闭门槛、修改指纹或重复刷新掩盖它。流程发布通过不能解释为该数据问题已解决。
