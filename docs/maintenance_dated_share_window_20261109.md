# 本地候选资料的完整日期窗口（2026-11-09）

本改动是显式选择的资料采集协议，不改 Top100、调仓日、交易约束、收益、成本或
任何版本参数。默认关闭 `MICROCAP_SHARE_DATED_WINDOW` 时仍走原单日接续。
开启为 `1` 后，已有认证底稿且需要公开后备源的证券，可以一次证明完整新增窗口。
301288 与 603028 在 2026-11-06 之前仍保留各自精确审阅/批准的原路线。

## 实际修复的问题

候选池中存在认证截至 2026-10-29 的非当前成员。逐日重复抓同一个发行人完整历史
会反复请求相同信息；发生正常股本变化时，原“股本不变”协议还会正确地拒绝推进。
新协议既支持不变，也支持认证截止日之后有完整独立来源支持的变化，不把正常新增
资料标为历史迁移。真实读回表明以下五只的原认证边界均为 **2026-10-29**：

| 证券 | 提供方变化日期 | 新总股数（股） |
| --- | --- | ---: |
| 603709 | 2026-10-30 | 163,213,999 |
| 300254 | 2026-10-30 | 271,188,563 |
| 688619 | 2026-11-03 | 184,553,586 |
| 688355 | 2026-11-04 | 123,689,482 |
| 301229 | 2026-11-06 | 182,914,165 |

这些数字由当日逐日 Eastmoney 市值表、完整 Eastmoney 事件清单和 Sina 总股本
完整历史交叉核验。603709、300254 的公司公告也已另行查看：前者注销 21,060 股，
后者增加 13,980,000 股，均指向 10 月 30 日。协议仍只声明提供方日期，不将其
自动升级为法律生效日。本地阶段没有修改生产历史文件或发送报告。

交易日历仍使用同一个独立提供方、参数、30 秒时限和覆盖检查。内存缓存从
4 个日期键扩大到 32 个，避免六个新增交易日的递归来源校验相互淘汰缓存，
进而为每只证券重复下载同一份完整日历。没有新持久日历或交易日推断。

## 不能放宽的条件

- 原股本状态和完整来源链先通过原生读回，再收集新增窗口。
- 认证边界日加每个新增交易日必须都有带日期的市值表原始行，分页、证券、交易所、
  日期、整数股数及“原始收盘价 × 总股数 = 总市值”全部吻合。缺日不能推断或填充。
- 边界日必须复现原认证股数。Sina 之前最后一项也必须一致；不一致仍要求精确历史迁移。
- 每个新变化要有唯一的 Sina / Eastmoney 事件对应，END_DATE、LISTING_DATE 和
  总股数一致；整个日序列必须精确复现这些变化。未知、零变化新事件继续拒绝。
- 迟发的旧期报告只有在两个资本日期均不晚于旧边界，并且股数精确复现已保护旧曲线时，
  才属于纯重复披露；不能用迟发报告改变旧认证数量。
- 完整清单中的未来事件仍走原精确计划/PDF审阅门槛。收盘时钟、同次观察、TLS、
  原始响应/回执哈希和当前总股数交叉核对均保留；当前报价不用于冒充历史日期。
- 仅在原 CSV 字节之后追加已证明的新行。不删、改、舍入旧值。普通发布异常回退原 CSV
  和原状态；并发字节变化保留不完整标记，不覆盖其他执行者。
- 同一证券、边界、目标和候选哈希使用独立目录。已完成 HTTP 响应和原回执可验证复用，
  原观察时间保留；请求耗尽标记阻止无依据重启同一预算。
